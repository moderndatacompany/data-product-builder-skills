# Migrate Data Product — DataOS 1.0 → Vulcan 2.0

Migrate an existing DataOS 1.0 data product to a Vulcan 2.0 project. Be literal, not creative: 1.0 business logic (joins, filters, aggregation formulas, quality thresholds) is the source of truth. This skill's job is re-platforming the *data-product build* — models, semantics, dq, tests, audits — not redesigning it and not moving data.

**Out of scope, explicitly**: whether the source tables are physically present in the target engine/depot, and any data-copy/backfill work to get them there, is not this skill's concern. Assume whatever the target `config.yaml` gateway points at is already queryable. If the user separately needs raw data moved between warehouses (e.g. a lakehouse-to-Postgres copy), that's a different, infrastructure-level task — flag it as a prerequisite and move on, don't try to plan or script it here.

**Language note**: Vulcan is anti-pipeline. Never say "pipeline" — say "model DAG", "data product", or "model layers."

> **Requires**: a 1.0 data product directory (DP Hub layout, see below) available on disk, and the `dpbs-docs/` grounding docs + `vulcan` CLI installed via `npx dataproduct-builder-skills` (same prerequisite as `build-data-product`).

---

## Why this is a distinct skill

1.0 splits one data product across several decoupled DataOS resources — a DP Hub spec, a Cube.js Lens semantic layer, one or more Flare ETL workflows, Soda quality workflows, and bundle/infra wiring — often living in different folders or even different repos, connected only by dataset refs and bitbucket paths. 2.0 (Vulcan) collapses all of that into one project where a single file's `MODEL()` block owns contract + lineage + assertions together.

Migrating well means: locate every 1.0 resource for a given output table, reconstruct the *combined* lineage (Flare ETL logic + Cube SQL wrapper are usually two hops of the same pipe), and re-express it as one Vulcan model — not a literal file-for-file copy.

The 1.0 layout below (DP Hub spec, `sqls/`+`tables/` Cube pair, Flare workflows, Soda QC) is a reused house pattern, not specific to any one client project — expect to see it recur under different naming (e.g. a different domain prefix than `cadp`) across different 1.0 codebases.

## 1.0 → 2.0 Concept Map

Ground every translation decision in this table. Read the referenced 1.0 file(s) in full before writing the 2.0 equivalent.

| 1.0 (DataOS 1.0 / Cube.js Lens)                                            | 2.0 (Vulcan)                                                      | Notes                                                                                                                                                                                          |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dph/dp-spec.yaml` (`type: data` resource) — description, tags, collaborators, `inputs[]`/`outputs[]` dataset refs, `ports.lens` ref | `usage.yaml` (good_for/not_for/caveats/references) + `config.yaml` name/tags/users + implicit `depends_on` graph across `models/*.sql` | `inputs[]` become the source tables your bronze/staging models read from; `outputs[]` become your gold model names |
| `dph/dp-scanner.yaml`                                                       | No 2.0 equivalent — Nilus Metadata Workflow scan is orchestrated outside the project | Note as N/A in the migration map, don't invent a file |
| `semantic-model/deployment.yaml` (`type: lens` resource — Cube.js API, repo/lensBaseDir, api/worker/router compute) | `<name>-deploy.yaml` generated by `vulcan create_deploy_yaml` — `spec.repo`, `spec.workflow.schedule`, `spec.api.replicas` | Cube's separate api/worker/router pods collapse into Vulcan's single deploy manifest; cron replaces Lens's scheduled refresh |
| `semantic-model/model/tables/*.yaml` (Cube `tables:` — `dimensions`, `measures`, `sql: {{ load_sql(...) }}`) | `models/semantics/*.yml` (`kind: semantic` — `dimensions:`, `measures:`) | Cube measure `type` values (count, count_distinct, sum, avg, min, max) map 1:1 to Vulcan measure `type`. Cube `sql: "{TABLE.col}"` → Vulcan `expression: "{model.COL}"`. Vulcan additionally requires every measure-referenced column to appear in `dimensions:` (Cube does not enforce this) |
| `semantic-model/model/sqls/*.sql` (thin `SELECT ... FROM <prebuilt_output_table>`) | Folded into the gold model's `MODEL()` SELECT in `models/<domain>/*.sql` — NOT copied as-is | This file alone is not the transform — it just reads a table some other job already built. Find that job (usually `build/data-processing/*.yaml`) to get the real logic |
| `semantic-model/model/views/*.yaml` (Cube `views:` — rollup/composite layer built on top of one or more `tables:`) | `models/metrics/*.yml` (`kind: metric`) when the view is a measure-over-time rollup; a second `kind: semantic` model with `joins:` when it's a cross-table composite | Not every 1.0 project has this layer (absent in `otis`, present in some others) — check for a `views/` subfolder before assuming it doesn't exist |
| `build/data-processing/*.yaml` (`type: workflow`, Flare/Spark DAG — `inputs[]` raw datasets, `steps[].sql`, `outputs[]`) | The bulk of the gold (or staging) model's SELECT in `models/<domain>/*.sql` | This is where the actual joins/filters/aggregations live in 1.0. Combine this SQL with the Cube sql wrapper's output columns to reconstruct the full lineage |
| `build/slos/*-qc.yaml` (`type: workflow`, `stack: soda+python`, `checks:` list) | `dq/{model_name}.yml` (`kind: dq`, `rules:`) + blocking checks promoted to `assertions(...)` in the `MODEL()` block | See Soda→Vulcan check mapping below. Soda `schema:`/uniqueness checks that must never pass bad data → promote to blocking `assertions`; monitoring-only checks → `dq/` |
| `build/activation/*` (e.g. an LLM-facing activation deployment) | No established 2.0 mapping yet | Out of scope for this skill — note its existence in the migration map as a gap, don't invent a Vulcan equivalent |
| `semantic-model/model/user_groups.yaml`                                    | `config.yaml` `users:` (+ RBAC handled by DataOS, not Vulcan project files) | Only migrate names needed as model `owner` values |
| `bundle/bundle.yaml`                                                       | No direct 2.0 file — Vulcan projects deploy as one resource, not a bundle of resources | Note as collapsed, not migrated |
| `infra/depot/<engine>/*.yaml` (per-source connection resource)             | A `type: depot` gateway connection in `config.yaml` (`dataos://<depot_name>`) | The depot itself (and whether it has data) is out of scope — this skill only needs to know the target engine so it can generate dialect-correct components; see Engine Awareness below |
| `infra/cluster/*.yaml` (compute cluster resources — e.g. minerva, themis) | No 2.0 equivalent — Vulcan/DataOS 2.0 compute is managed by the platform, not declared per-project | Note as N/A |
| `infra/bitbucket.yaml`                                                     | `spec.repo.secret` in the deploy manifest | Same credential, new location |
| (none — 1.0 has no unit-test concept)                                     | `tests/*.yml`                                                     | New in 2.0 — write at least one test per migrated gold model per the `build-data-product` skill's Group E rules |
| (none — 1.0 has no metrics layer, only Cube measures/views)               | `models/metrics/*.yml` (`kind: metric`)                            | Only create if the user confirms a genuine time-series metric is needed, or a 1.0 `views:` file already implies one; do not invent metrics that 1.0 didn't have |
| (none — 1.0 Cube tables have no `ai_context`/`behavior`)                  | `ai_context:` and `behavior:` blocks in `models/semantics/*.yml`   | New in 2.0 — draft minimally from the 1.0 `description` fields, mark low-confidence ones as `[Assumption]` per the `design-data-product` Step 2.6/2.7 rules; do not fabricate business framing not present in 1.0 |

**Soda check → Vulcan DQ/assertion mapping** (`build/slos/*-qc.yaml` `checks:` entries):

| Soda check pattern                                  | Vulcan equivalent                                                                                     |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `schema: ... fail: when required column missing`     | `not_null`/column presence via `columns(...)` in `MODEL()` — structural, not a DQ rule                 |
| `missing_count(col) = 0` / `missing_percent(col) < X%` | `completeness` DQ rule (`dq/*.yml`); promote to blocking `not_null` assertion if the 1.0 check was on a grain/key column |
| `duplicate_count(col) = 0`                            | `uniqueness` DQ rule, or blocking `unique_values`/`unique_combination_of_columns` assertion if on the grain |
| `freshness(col) < Xd`                                 | `timeliness` DQ rule                                                                                    |
| `invalid_percent(col) < X%` with `valid values: [...]` | `validity` DQ rule (`accepted_values`-style expression)                                                 |
| Referential/FK-style checks                           | `validity` or `consistency` DQ rule (`integrity` is not a valid Vulcan DQ dimension)                    |
| Row-count / volume checks                             | `coverage` DQ rule                                                                                      |

**Before writing any translated `dq/*.yml` rule**, verify its operator direction matches the human-readable name/description you're carrying over — a translated rule that inverts the original check's polarity (e.g. a rule named "no missing user IDs" but written to fail when the count *isn't* zero) is a defect, not a style choice.

## Engine Awareness

The 1.0 source and the 2.0 target may run on the same engine, or the migration may include an engine change (e.g. Snowflake → Postgres) decided elsewhere. Either way, this skill only cares about **authoring the components correctly for the target engine** — not about how or whether the underlying data gets there.

1. Confirm the target engine (usually already fixed by the target `config.yaml`/depot the user hands you, or ask if genuinely unset).
2. Before writing any physical model SQL or semantic YAML, read `skills/build-data-product/engines/<target_engine>.md` (if present) alongside `dpbs-docs/vulcan-examples/<target_engine>/` — same as `build-data-product`'s own Per-Engine Reference Notes. Pay particular attention to:
   - identifier casing convention (e.g. Snowflake uppercase vs. everyone else lowercase)
   - the target engine's date/time function syntax, since 1.0 Flare/Cube SQL almost always embeds source-engine-specific date arithmetic that will not survive a straight copy across engines
   - whether the target engine wants an explicit `columns()` block vs. inferred types
3. If the target engine differs from the 1.0 source, treat every function call in the reconstructed transform SQL (Stage 1 below) as a translation candidate, not just a syntax check — flag each one in `migration-map.md` even if you're fairly confident of the equivalent, so the user can verify.
4. This skill doesn't plan, script, or gate on *moving* data between engines/depots — that's a separate infrastructure task, tell the user so if they need it. It does still require *verifying* that whatever table you're about to wire a model to is actually populated (see Physical-Passthrough Sources below) — that's not data movement, it's confirming the source you picked is the right one.

## Workflow

### Stage 0: LOCATE & INVENTORY

**Goal**: Find the 1.0 project root and build a complete resource inventory before touching anything.

1. Ask the user for the 1.0 project directory if not already given (e.g. `1.0-dp/<name>/`).
2. Walk it and classify every file against the Concept Map above. Expect this shape (some pieces may be missing, and some 1.0 projects add a `views/` or `activation/` subfolder the Concept Map also covers — note gaps and extras, don't guess):
   ```
   <name>/
     dph/                    — dp-spec.yaml, dp-scanner.yaml
     semantic-model/
       deployment.yaml        — lens resource
       model/
         sqls/*.sql           — thin wrapper SELECTs
         tables/*.yaml        — Cube dimensions/measures
         views/*.yaml         — optional: Cube rollup/composite layer
         user_groups.yaml
     build/
       data-processing/*.yaml — Flare ETL workflows (real transform logic)
       slos/*-qc.yaml         — Soda quality workflows
       activation/*           — optional: LLM/serving-layer deployment, no 2.0 mapping
     bundle/bundle.yaml
     infra/
       bitbucket.yaml
       cluster/*.yaml
       depot/<engine>/*.yaml
   ```
3. For each output table in `dph/dp-spec.yaml` `outputs[]`, find its three matching artifacts:
   - `semantic-model/model/tables/<name>.yaml` (dimensions/measures)
   - `semantic-model/model/sqls/<name>.sql` (wrapper SELECT — tells you the *prebuilt* table it reads)
   - the `build/data-processing/*.yaml` whose `outputs[].dataset` matches that prebuilt table (real transform SQL)

   **If no matching `build/data-processing/*.yaml` exists, don't jump straight to "blocker."** A missing Flare job commonly means the 1.0 product is a **Lens-over-prebuilt** pattern: the Cube wrapper's source table is already a physical, queryable table in the target warehouse (built by some job outside this repo, or just resident data) — there's no transform to reconstruct because there's nothing to rebuild. Check this before asking the user for another repo:
   - Search the target engine's catalog for the wrapper SELECT's source table — use the Data Product MCP `search(index="table_search_index", ...)` tool (same one `design-data-product` uses) if connected, otherwise ask the user to confirm the table exists in the target warehouse.
   - **If found and populated** → this output doesn't need ETL reconstruction at all. Plan a thin **VIEW** model that selects straight from the physical table, with Cube-guided semantics on top (see Physical-Passthrough Sources below). This is not a lesser migration — it's the correct shape for this kind of 1.0 product.
   - **If not found, or found but genuinely empty with no populated alternative** → now it's a real blocker: the transform logic lives in a different repo/job and can't be reconstructed from what's on disk. Ask the user for it or flag it; do not guess the transform.
   - **If found under a different schema/path than the 1.0 Cube wrapper references** (e.g. 1.0 hardcodes `LEGACY_CATALOG.SCHEMA_A` but the catalog search surfaces the same table under `NEW_CATALOG.SCHEMA_B`) — don't assume either path is automatically right. See the row-count check below.

4. Present the inventory as a table: `1.0 output table | tables/*.yaml | sqls/*.sql | matching build/data-processing/*.yaml | matching build/slos/*-qc.yaml | physical table confirmed?`. Mark any cell "NOT FOUND" honestly.

**Gate**: do not proceed to Stage 1 until every output table's row is either fully resolved (ETL reconstructable, or a confirmed-populated physical table found) or explicitly flagged as a blocker the user has acknowledged.

### Physical-Passthrough Sources (no ETL to reconstruct)

When Stage 0 confirms an output is a physical table already resident in the target warehouse, the migration for that model is: **thin VIEW model reading the physical table + Cube-guided semantics on top** — not a from-scratch semantic redesign, not an ETL rebuild.

1. **Catalog/data-source search can surface more than one candidate path** for the same logical table (a currently-synced schema vs. the 1.0 product's original hardcoded path). Do not pick one just because it matched the search query first — **verify row counts on every candidate before wiring a model to it**. A table existing in the catalog proves the schema is registered, not that it has data.
2. If a candidate table returns zero rows, don't accept it as correct and move on — search sibling schemas/catalogs for a populated twin (same table name, different schema/database) before concluding the data genuinely isn't available anywhere. Record which path was actually populated in `migration-map.md`, not just which path was found first.
3. Once counts are in, if more than one candidate is populated, prefer the path the 1.0 Cube wrapper SQL actually points to — it's the one already treated as authoritative by the running 1.0 product; a different populated path with the same schema is not automatically equivalent data.
4. If the user names a specific source as ground truth ("MCP is ground truth", "use the depot path", etc.) when multiple candidates exist, follow that — but still run the row-count check on their chosen path before finalizing, and surface it plainly if their preferred path turns out empty while another candidate is populated. Don't silently override their instruction, and don't silently accept an empty table either — report the conflict and ask.
5. **Author fresh Vulcan semantics from the 1.0 Cube dims/measures — never reuse or import an existing warehouse/catalog Semantic object**, even if the same tool that found the physical table also surfaces a semantic model built on top of it. The 1.0 Cube `tables/*.yaml` is the consumer contract to carry forward (people already query those measures/dimensions by name); the warehouse's own semantic layer, if one exists, is out of scope to import — that would be reusing someone else's redesign, not migrating the 1.0 product.
6. Physical-passthrough models are `kind VIEW` almost by definition — there's no transform to materialize, just a typed read of an existing table.

### Stage 1: BUILD THE MIGRATION MAP

**Goal**: Produce `migration-map.md` — the artifact this skill hands to `build-data-product` in place of (or alongside) a hand-written `data-product-plan.md`.

For each output table, extract and record:

- **Grain**: infer from the Cube `primary_key: true` dimension(s) in `tables/*.yaml`, cross-checked against the `GROUP BY` in `build/data-processing/*.yaml`'s SQL. If they disagree, stop and ask the user which is authoritative.
- **Source tables**: every `inputs[].dataset` used by the matching `build/data-processing/*.yaml`, plus any `depends_on` referenced by the Cube wrapper SQL.
- **Transform logic**: the full SQL from `build/data-processing/*.yaml` `steps[].sql` — this becomes the base of the new Vulcan model's SELECT. Note any Flare-specific syntax (e.g. `dataos://` dataset paths, Spark SQL functions) that needs translating to the target engine's dialect — see Engine Awareness above.
- **Dimensions & measures**: copied from `tables/*.yaml`, types mapped per the Concept Map.
- **Quality rules**: copied from the matching `build/slos/*-qc.yaml`, classified per the Soda→Vulcan mapping table.
- **Target engine**: confirmed per Engine Awareness above; every engine-specific SQL function found in the Flare SQL flagged as a translation TODO if the target engine differs from source.

Write `migration-map.md` using this structure (mirrors `data-product-plan.md`'s Section 13 Model Architecture + Section 15 Quality Rules so it slots into `build-data-product` cleanly):

### Stage 2: HANDOFF TO BUILD

**Goal**: Hand `migration-map.md` to the `build-data-product` skill as its input spec.

1. Tell the user: "Migration map ready. Handing off to the build workflow — it will scaffold the Vulcan project, generate models/semantics/dq/tests component-by-component, and run `vulcan plan`/`evaluate` to validate against the target engine."
2. Invoke `build-data-product`. `migration-map.md` qualifies as a canonical spec under its Gate Check (same standing as `data-product-plan.md`) — its **Per-Model Migration** section is the equivalent of Section 13 (Model Architecture) and its **Quality rules** entries are the equivalent of Section 15, so `build-data-product` should proceed straight to Stage 0 without running Spec Intake or the reduced-confidence disclaimer.
3. One migration-specific addition to `build-data-product`'s normal flow: for each model, after `vulcan evaluate`, run a **row-count / spot-value parity check** against the original 1.0 output table (if still queryable) to confirm the re-platformed model produces equivalent results, not just syntactically-valid ones. For a **physical-passthrough** model this is a lighter check — same row count as the confirmed physical source (Physical-Passthrough Sources above already resolved which physical table that is; parity here just confirms the VIEW reads it faithfully). For an **ETL-reconstruction** model it's the fuller check — verify recomputed measure values match the 1.0 output, not just row counts. Surface any material discrepancy to the user before moving to the next model — do not silently accept a mismatch as "close enough." Skip this step (and say so) if the 1.0 output table isn't reachable for comparison — don't treat that as a blocker on its own, since verifying data reachability isn't this skill's job.

## Core Principles

1. **1.0 logic is ground truth** — never alter a join, filter, or formula found in `build/data-processing/*.yaml` SQL unless the user asks. Migration ≠ redesign.
2. **Reconstruct, don't copy the wrapper** — the Cube `sqls/*.sql` file is a decoy; it reads a table some other job built. Trace to the Flare workflow for real logic — but first check whether that table is simply already physical and populated in the target warehouse, in which case there is no logic to trace to (see Physical-Passthrough Sources).
3. **Flag, don't guess, missing links** — if a 1.0 output table has no matching `build/data-processing/*.yaml` AND no confirmed populated physical table anywhere reachable, say so and stop; do not fabricate transform SQL.
4. **Catalog presence ≠ data presence** — never wire a model to a table just because a catalog/MCP search returned it. Confirm row count before trusting it as the real source; an empty table with the right name is not the right source.
5. **Never reuse an existing warehouse/catalog semantic layer** — even when locating physical tables surfaces one. The 1.0 Cube `tables/*.yaml` dims/measures are the contract to carry forward; author fresh Vulcan semantics from that, not by importing someone else's already-built semantic object.
6. **Engine changes are explicit** — if the target engine differs from 1.0's, every dialect-specific function is a translation TODO, verified against `skills/build-data-product/engines/<target_engine>.md` and `dpbs-docs/vulcan-examples/<target_engine>/`, never assumed portable.
7. **New 2.0 concepts are additive, not inventive** — `ai_context`, `behavior`, `metrics`, `tests` don't exist in 1.0. Draft them minimally from what 1.0 actually says (descriptions, tags); mark anything not grounded in 1.0 source as `[Assumption]`.
8. **Data movement is not this skill's job** — never plan, script, or gate progress on copying data between engines/depots. Assume the target is queryable and build the components correctly for it.
